Hosted Control Planes on a laptop

A management cluster runs the control planes of other clusters as pods, and separate workers talk only to their own API through a published endpoint. It has the same shape as OpenShift HCP (ROSA HCP), built from upstream pieces so you can break it and understand it.

1 management cluster 2 hosted clusters 1 worker per NodePool ~3.3 GB of RAM in total

Upgrades

The control plane and the workers upgrade separately

Same as HCP: first you bump the control plane version, which only restarts pods on the management cluster. The workers stay on the previous version until you upgrade their NodePool.

Get started

Up and running in about 5 minutes

You need podman (or docker) with a 6 CPU, 10–12 GB VM, kind 0.33 or later, helm and python3. The lab downloads its own kubectl and uses its own kubeconfigs, so it never touches ~/.kube/config.

# once, if the VM is too small
podman machine stop && podman machine set --cpus 6 --memory 12288 && podman machine start

./scripts/01-mgmt-cluster.sh               # management cluster
./scripts/02-addons.sh                     # cert-manager, MetalLB, Kamaji
./scripts/03-hosted-cluster.sh tenant-a 1  # hosted cluster in slot 1 → 127.0.0.1:31441
./scripts/04-nodepool.sh tenant-a 1        # one worker in its data plane
./scripts/status.sh                        # overview

source env.sh
kubectl get tcp -A                         # control planes, seen from the management cluster
hkubectl tenant-a get nodes                # inside the hosted cluster
Practice

Exercises

  1. The tenant cannot see its control plane. hkubectl tenant-a get pods -n kube-system shows no apiserver and no etcd.
  2. No konnectivity, no logs. Delete the konnectivity-agent DaemonSet and try logs: No agent available. Kamaji brings it back in about 10 seconds.
  3. The control plane goes down, the apps keep running. Scale the tenant's Deployment to 0 and check crictl ps on the worker.
  4. Control plane HA. Set replicas to 2 and watch them spread across both management nodes.
  5. Two-phase upgrade. The TCP first, then the NodePool.
  6. Scale the NodePool. 04-nodepool.sh tenant-a 3 and back to 1, drain included.
  7. Lose a management cluster node. podman stop hcp-mgmt-worker2: which control plane goes down? What about its etcd on a local PVC?
Keep in mind

Differences from real HCP

  • No OpenShift components: no openshift-apiserver, oauth, CVO or Routes. It is upstream Kubernetes with the same topology.
  • HCP runs each component as its own Deployment. Kamaji packs apiserver, controller-manager, scheduler and konnectivity-server into one pod with 4 containers.
  • Workers are not in another account or VPC: they share the kind network with the management cluster.
  • There is no NodePool CRD: a script plays the controller.
What broke while building it

Three problems you will run into

kube-proxy: nf_conntrack_max: permission denied

kube-proxy rewrites the value whenever it is not exactly 32768 × CPUs, and inside a container it is not allowed to. 01-mgmt-cluster.sh sets that exact value on the container host. Re-run it after restarting the VM or changing its CPUs.

Pods stuck in ContainerCreating with flannel

flannel delegates to the bridge CNI plugin, and kindest/node images do not ship it. That is why the lab uses kindnet, which comes inside the image itself.

logs and exec: No agent available

The konnectivity-agent is not running, almost always because pod networking is broken. Since kubectl logs does not work either, debug from the node: podman exec <worker> crictl logs ….
